# Sellout Watcher — orientation for new agent sessions

A static-site dashboard tracking how fast Park & Rec classes sell out during
registration windows. Currently covers Arlington County, VA's summer 2026
window; designed to extend to more counties and seasons (see `ROADMAP.md`).

Live site: <https://selloutwatcher.com/>. Custom domain is configured via
the GitHub Pages web UI (Settings → Pages → Custom domain). A `CNAME` file
exists at the repo root but it's GitHub-managed (auto-committed when the
domain was set in the UI) — don't edit or remove it manually.

(The GitHub Pages subdomain <https://mkang32.github.io/arlrec-monitor/>
still works as a fallback.)

## Stack at a glance

- **Scraper**: Python (`scraper/`) using `curl_cffi` (browser TLS impersonation
  to get past Cloudflare). Polls the public Vermont Systems WebTrac catalog at
  `vaarlingtonweb.myvscloud.com`.
- **Storage**: a single SQLite file `data/snapshots.sqlite` committed to the
  repo. Tables: `sections`, `snapshots`, `alerts_sent`, `currently_open` (a
  materialized analysis view, rebuilt on every dump).
- **Scheduling + execution**: GitHub Actions (`.github/workflows/`).
- **Site**: pure static HTML served by GitHub Pages from the repo root.
- **Alerts**: Gmail SMTP + ntfy.sh push + optional Slack/Discord webhook.
- **Domain**: `selloutwatcher.com` (live; configured via GH Pages UI).

## How to run things locally

```bash
# Scrape one event (status only, fast)
python3 -m scraper.scrape --mode event --event ENJOYSUMMER2 --skip-counts

# Scrape with enrollment counts (~2 min per ~250 sections)
python3 -m scraper.scrape --mode event --event ENJOYSUMMER2

# Refresh type tagging for ALL sections (run after adding new event days)
python3 -m scraper.scrape --mode types

# Regenerate dashboard + CSVs + materialized currently_open table
python3 -m scraper.dump

# Regenerate analysis page (reads data/snapshots.sqlite)
python3 website/build_page.py
# With production URL substituted into OG tags:
SITE_URL=https://selloutwatcher.com python3 website/build_page.py

# Regenerate social-preview image
python3 website/build_og_image.py

# Preview the whole site
python3 -m http.server 8000
# then http://localhost:8000/
```

## Key gotchas (things that took hours to figure out)

### Scraping
- **Cloudflare blocks plain HTTP clients.** Must use `curl_cffi` with a
  browser TLS fingerprint. `requests` / `urllib` / plain `curl` all return 403.
- **Cloudflare adapts.** A working fingerprint may stop working within a day.
  `webtrac.py` maintains `IMPERSONATE_CHAIN` and rotates on 403. Add new
  fingerprints to the front of the chain when others fail.
- **From GH Actions runner IPs**: only Safari/Firefox fingerprints work.
  Chrome impersonations are blocked from datacenter IPs.
- **Queue-it.** Around registration-opening time, the site shows a virtual
  waiting room (HTTP 200 with `<title>Queue-it</title>`, no CSRF token). Our
  scraper detects this and soft-skips the iteration. Useful data resumes ~15-30
  min after the queue clears.
- **No wildcard search.** WebTrac's search requires a filter. We iterate the
  `type` dropdown (`config.ALL_TYPES`, 39 entries — all WebTrac types) for
  catalog scans, and use `registrationevent` filters for hot-window polling.
- **Pagination is `Page=N`** (capital P). Default page size is 25; total count
  appears in the "Showing results X-Y of Z" text.
- **Be polite.** `webtrac.py` enforces a 0.5s minimum delay between requests.

### Data interpretation
- **`reg_event` is unstable.** Arlington admins use staged tags
  (`ENJOYSUMMER1`/`ENJOYSUMMER2`) on respective opening days, then re-tag
  everything to `ENJOYSUMMER` later. Don't rely on the current `reg_event`
  value to determine which registration day a section opened on. Instead, use
  `_opens_at_before(scarce_dt)` in `dump.py` — it picks the latest known
  `opens_at` ≤ the first observed scarce timestamp. Self-correcting and
  immune to upstream re-tagging.
- **`Unavailable` is overloaded.** Means *both* "pre-registration" *and*
  "post-class-started." Disambiguate via the section's `date_start` + the
  known registration-open time.
- **`first_scarce_ts` is the source of truth** for sell-out timing — derived
  from snapshot history, not from any WebTrac field.

### Workflows
- **GitHub Actions cron is unreliable.** Scheduled events can be silently
  dropped (happened May 12 and May 13). Mitigations in place:
  - Primary + backup cron entries (`40 15` and `48 15` UTC) for hot-window
  - `watchdog.yml` checks at `15:45` and `15:55` UTC and alerts if hot-window
    didn't fire
  - Manual fallback: `gh workflow run hot-window -R mkang32/arlrec-monitor -f event=X -f skip_wait=true`
- **Concurrency lock.** `ambient`, `tail`, `hot-window`, `smoke` all share
  `concurrency: scrape-write` (serializes git pushes). Queued runs get
  cancelled if a new one queues — this is why hot-window's inline `count_pass`
  exists (ambient can't run while hot-window holds the lock).
- **Robust commit pattern.** Every workflow commit uses the
  "save sqlite → reset → pull → restore sqlite → regenerate → commit" pattern.
  Surviving git conflicts on binary files (sqlite) is the whole game.
- **Final-pass safety net.** `hot-window.yml` has an `if: always()` final
  enrollment-counts step that runs even if the poll loop crashed.

### Site structure
- **Dashboard URL deep-links.** Filter widgets emit `data-url-key="..."`.
  Loading `dashboard/?type=gymnastics` auto-applies the type filter. A
  "Filtered by:" banner shows the active filters with a clear button.
- **Anchor links.** Dashboard has `#sellout-section` and `#open-section`
  anchors so chart clicks on the analysis page can land on the right table.
- **Bin labels.** `Instant (<20 min)` / `Under 1 hour` / `1–6 hours` /
  `6–24 hours` / `Multi-day`. The "Instant" bin is a measurement floor (faster
  than our polling cadence). Don't show "fastest sellout" times — they're
  misleading. We show count + ratio in the fast-sellouts bucket instead.
- **Type-label fallback.** Sections with no type_code get `Other` as the
  label (consistently across dashboard, analysis page, and CSVs).

## Secrets configured in GitHub repo

- `ALERT_GMAIL_USER` — sender/recipient gmail address
- `ALERT_GMAIL_PASS` — Gmail App Password (16 chars; spaces tolerated)
- `ALERT_WEBHOOK_URL` — Slack/Discord incoming webhook (optional)
- `ALERT_NTFY_TOPIC` — ntfy.sh topic name (optional)
